# STATE_AND_DECISIONS.md

## THE DECISION LOG

* **Track 03 — AI Revenue Recovery (over Track 04, 02, 01, 05)**
  * **Why:** Best balance of finance-domain fit and solo-buildable scope. More forgiving demo surface than Track 04 (reconciliation requires harder-to-fake realistic data); avoids Track 02's formal precision/recall ML evaluation burden; avoids Track 01's live Razorpay API integration risk; avoids Track 05's open-ended scoping cost.
  * **What breaks if reversed:** Entire schema, root-cause list, recovery-action design, and differentiation strategy are built specifically around payment/checkout/invoice recovery. Switching tracks invalidates the whole plan, not just a component.

* **Solo build, full scope retained (not narrowed) for 14 days**
  * **Why:** User confirmed no competing 14-day commitments and heavy AI-assisted coding capability, making full scope realistic if build order is strictly sequenced.
  * **What breaks if reversed:** If scope is cut mid-build after this decision, partially-built interdependent stages (rules→ML→LLM→dashboard) may be left inconsistent; if scope is expanded further, the 14-day timeline breaks.

* **Full loop scope: checkout abandonment + payment failure + overdue invoice, not payment failures only**
  * **Why:** User explicitly chose full loop over a narrower single-path scope.
  * **What breaks if reversed:** Schema, root-cause mapping, and the single-shared-engine architecture rule all assume three event types feeding one system; narrowing removes two of the three branches the shared engine is designed to handle.

* **Single shared recovery engine (`classify()`, `decide_action()`, `execute_action()`) for all three event types — not three parallel per-path systems**
  * **Why:** Identified as the single highest scope-fragmentation risk for a solo 14-day build; without this rule, AI-assisted code generation defaults to duplicated per-event-type logic.
  * **What breaks if reversed:** Triples effective build/maintenance surface, defeats the "full loop, one system" positioning used in the differentiation strategy, and risks inconsistent compliance/audit logic across paths.

* **Exclude fraud/DDOS/spam detection from scope**
  * **Why:** That problem belongs to Track 02 (Risk Manager); including it dilutes Track 03 positioning and adds unrelated ML evaluation burden.
  * **What breaks if reversed:** Scope bleeds into another track's judged category, diluting "problem taste" criterion and adding unplanned build time.

* **6 payment-failure root causes locked: insufficient funds, card declined, bank timeout/gateway error, 3DS auth failure, expired card, network failure**
  * **Why:** Covers realistic failure diversity without unbounded classification scope; network failure added deliberately, device-switch-off and DDOS explicitly rejected as miscategorized.
  * **What breaks if reversed:** Downstream classify() logic, error_reason mapping, and demo scenarios are all built against exactly these 6 categories.

* **No dataset/API sandbox assumed from Razorpay for Track 03 — self-generate all data**
  * **Why:** Confirmed no official source exists for this track (unlike Track 01, which explicitly gets Razorpay test-mode APIs); could not verify further via search due to JS-rendered site.
  * **What breaks if reversed:** If an official dataset is later found, current synthetic-data-dependent architecture and "own your data pipeline" differentiation argument would need re-evaluation, not blind replacement.

* **Data schema uses Razorpay-aligned field names (id, entity, amount in paise, status, error_code, error_description, error_source, error_step, error_reason) rather than generic custom field names**
  * **Why:** Makes synthetic data look production-grade and domain-aware without claiming to match a real hidden judge dataset (confirmed no such hidden test set exists — judges review via repo/video/interview, not by running against their own data).
  * **What breaks if reversed:** Loses the "understands the real domain" signal that differentiates from generic-looking synthetic data; error_reason field would lose its direct mapping to the 6 locked root causes.

* **Static seed data (JSON) must be loaded into a live, mutable database (SQLite) — not read directly as the operating dataset**
  * **Why:** User identified that a frozen dataset cannot demonstrate a "moving," live-acting agent system.
  * **What breaks if reversed:** Dashboard and audit trail would show static, unchanging state, undermining the "live system" proof requirements established later in the same decision set.

* **LLM provider: Gemini API, not Claude API**
  * **Why:** User already has Gemini API access; no functional requirement favors Claude for this project's tasks (message generation, structured JSON intent extraction); avoids setup/billing delay.
  * **What breaks if reversed:** Requires new API key provisioning and billing setup with no functional gain identified.

* **AI method split locked: rules/hard-coded logic for compliance and control decisions, ML for prediction/scoring, LLM restricted to language generation and structured intent extraction only — LLM never makes control decisions directly**
  * **Why:** Directly targets the official "AI judgment — right tool in right place, and where you chose not to use one" judging criterion; keeps compliance-critical logic auditable and non-hallucinating.
  * **What breaks if reversed:** If LLM is allowed to make control/compliance decisions directly, stopping rules and escalation logic become unauditable and unreliable, undermining the "would you trust it" judging criterion and the core differentiation strategy.

* **Hard-coded stopping/compliance rules are non-negotiable and must never be overridden by ML or LLM output**
  * **Why:** Named explicitly in Track 03's official "Bar" (compliant escalation, stopping rules); most solo competitors are expected to skip this, making it a deliberate differentiator.
  * **What breaks if reversed:** Removes the specific compliance-awareness differentiator and risks demoing an agent that could spam/retry indefinitely, contradicting stated judging criteria.

* **Two-surface limit: one Ops Dashboard + case detail thread folded into it — no separate customer-facing portal, no third portal unless spare time exists on days 12–13**
  * **Why:** More surfaces increase solo build risk and reduce polish-per-surface; judges reviewing quickly need one coherent thing to click through.
  * **What breaks if reversed:** Adding surfaces early risks the same shallow-breadth failure mode flagged earlier in planning (many things half-built vs one thing done well).

* **Live Agent Console added as a required, non-optional Stage 4 feature (event triggers, free-text reply box, visible reasoning panel, live audit trail feed, live-recomputing metrics)**
  * **Why:** Necessary to prove the system is genuinely reasoning live rather than hardcoded, both for the recorded video (no live judge interaction possible) and the panel interview (judges can test it directly); a static/scripted demo is vulnerable to a judge typing unanticipated input and breaking it instantly.
  * **What breaks if reversed:** Removes the primary mechanism for surviving judge skepticism about hardcoded/scripted responses; without it, the "AI judgment" and "would you trust it" criteria have no live evidence behind them.

* **Confidence-threshold handling required as real branching logic (low-confidence intent extraction routes to manual review, not auto-action)**
  * **Why:** Proves confidence scoring is functionally real rather than decorative; also serves as a demo scenario for ambiguous customer replies.
  * **What breaks if reversed:** Confidence scores become cosmetic; ambiguous inputs would be forced into auto-actions, contradicting the "compliant, bounded" requirement in Track 03's official Bar.

* **Self-consistency / mismatch check required (cross-check extracted reply intent against existing root_cause data before acting; flag conflicts instead of proceeding blindly)**
  * **Why:** Demonstrates the system cross-checks itself rather than blindly chaining LLM output into action — identified as a high-value, low-competition differentiator.
  * **What breaks if reversed:** Removes evidence of self-consistency checking, weakening the "would you trust it" criterion and one of the two highest-priority differentiators identified in this chat.

* **Demo/proof scenarios (multi-turn conversation, broken promise-to-pay, ambiguous replies, mid-conversation language switching, live cooldown enforcement, off-topic replies) treated as test cases against existing build, not as new architecture or separate features**
  * **Why:** Necessary to keep the proof requirements from silently expanding the 14-day build scope; these exercise existing logic rather than requiring new systems.
  * **What breaks if reversed:** Treating these as separate features to build (rather than inputs to test existing logic with) reintroduces the scope-blowout risk the single-engine rule was designed to prevent.

* **Headline metrics (recovery rate, ₹ recovered, etc.) must be reproducible/queryable live, not just stated in narration or slides**
  * **Why:** A claimed-but-not-inspectable number is indistinguishable from a fabricated one; judges cannot verify narration alone.
  * **What breaks if reversed:** Any pitch numbers become unverifiable claims, undermining the "measured money recovered" requirement explicitly stated in Track 03's official Bar.

* **Failure Recovery Log Protocol: whenever a real build failure occurs, resolve it live, confirm with user, then generate a standalone `.md` file documenting what broke/why/what worked — repeatable, not a one-time artifact**
  * **Why:** Required as source material for the application form's mandatory "what broke, and how you got out" field; must reflect a real failure, not a fabricated one.
  * **What breaks if reversed:** Without a real documented failure, the application answer to this required field would need to be fabricated or omitted.

* **Strict build order enforced (rules-only core loop → ML layer → LLM layer → dashboard → stress test), with no mid-build feature additions — new ideas go on a deferred list**
  * **Why:** Directly addresses user's stated risk: limited independent tech-stack knowledge combined with heavy AI-assisted coding creates high risk of context loss and architecture drift if steps are taken out of order.
  * **What breaks if reversed:** Out-of-order building was explicitly identified as the mechanism by which bugs and incomplete integration would most likely occur in this specific solo, AI-assisted build.

* **No autonomous multi-step code generation without explicit per-step user confirmation**
  * **Why:** User explicitly revoked earlier autonomous building behavior mid-session ("I don't want you to auto initiate anything without consulting with me").
  * **What breaks if reversed:** Violates a direct, explicit user instruction; risks the same uncontrolled drift (e.g., the divergent-schema incident from a separate chat) that prompted the instruction in the first place.

* **All previously generated code and data files discarded; project treated as research/analysis-complete, zero code written**
  * **Why:** Explicit user reset instruction.
  * **What breaks if reversed:** Any future reference to previously generated `generate_data.py`, `db.py`, or seeded database contents as if still active would contradict the user's explicit reset and reintroduce the exact schema-conflict problem this reset was meant to resolve.

* **Backend/frontend folder split: all backend-related folders (`data`, `scripts`, `db`, `engine`, `ml`, `llm`, `api`, `logs`) nested under one `backend/` root; `frontend/` kept separate at project root**
  * **Why:** User identified this as easier for independent deployment — backend becomes one deployable unit (own `requirements.txt`, `.env`) separate from a frontend deployed elsewhere (e.g. Vercel/Netlify).
  * **What breaks if reversed:** Deployment story reverts to a flat/mixed structure; import paths and relative file references already written against `backend/` as root (e.g. `db/db.py` resolving `data/` one level up) would break.

* **Claude does not execute project scripts on the user's behalf; user runs all scripts locally and pastes output back for verification**
  * **Why:** User explicitly corrected Claude for running `generate_data.py` on Claude's own sandboxed environment instead of the user's machine; user wants full local execution control.
  * **What breaks if reversed:** Violates explicit user correction; risks divergence between what Claude verifies internally and what actually exists in the user's real project folder.

* **Contact-hour compliance check evaluated on the payment's simulated `created_at` timestamp, not the real system wall clock (`datetime.now()`)**
  * **Why:** Using the real system clock made the check depend on when the developer happened to run the script, not on the simulated event's own timing — produced unrealistic all-or-nothing blocking across the whole batch.
  * **What breaks if reversed:** Contact-hour enforcement becomes non-deterministic and disconnected from the synthetic data's own timestamps, undermining the "live system reasoning about real event data" proof requirement.

* **9am–8pm contact window restriction applies only to customer-facing actions (`retry`, `reminder`); `escalate` bypasses this check entirely**
  * **Why:** Escalation is internal routing to a human queue, not customer contact — the rule exists to protect customers from off-hours contact, not to delay internal handoffs.
  * **What breaks if reversed:** Legitimate 7-day-no-response escalations would be incorrectly delayed by a rule designed for customer-facing messaging, weakening the auto-stop/escalate compliance guarantee.

* **`decide_action()` outcome field standardized to a fixed reason-code set: `executed`, `blocked_contact_hours`, `blocked_cooldown`, `blocked_already_stopped`, `blocked_already_escalated`. `blocked_max_retries` explicitly dropped; `escalated_no_response` explicitly not used as an outcome value**
  * **Why:** Max-retries transition already resolves to `action_type="stop", outcome="executed"` in the existing state-safety design — a separate `blocked_max_retries` code would be unreachable dead code, not a real branch. `escalated_no_response` context is preserved in `reasoning` text instead, keeping `outcome` values meaningfully small and auditable.
  * **What breaks if reversed:** Reintroducing `blocked_max_retries` as a literal branch would require restructuring the stop-transition logic (a bigger architectural change flagged and explicitly declined in this session); reintroducing `escalated_no_response` as an outcome fragments the outcome vocabulary without adding new information already captured in `reasoning`.

* **Invoice overdue auto-escalation (7-day no-response rule) uses `payment["days_overdue"]` for `invoice_overdue` events, not `created_at` event age; all other event types continue using `created_at` age**
  * **Why:** SoT section 3 explicitly defines `days_overdue` as the escalation timing input for invoices, distinct from event age used by the other two event types. Original implementation incorrectly applied `created_at` age uniformly across all three types, misclassifying invoice escalation timing.
  * **What breaks if reversed:** Invoice cases would escalate based on how long ago the event row was created rather than actual business overdue duration — verified via `verify_invoice_escalation.py` that these two measures diverge on real data (e.g. `age_days=7.7` with `days_overdue=3` must NOT escalate).

* **Fresh-DB protocol required for clean Stage 1 verification runs: `db/recovery.db` must be deleted and `db/db.py` re-run before re-running `core_loop.py` when testing rule-engine changes**
  * **Why:** `db.py`'s loader uses `INSERT OR REPLACE` only on `customers`/`payments`; it never clears `recovery_actions`/`messages`, so re-running the core loop without wiping the DB tests against accumulated prior-run history, not a clean first-cycle state — this produced a misleading initial "re-verification" that was actually a second cycle.
  * **What breaks if reversed:** Future rule-engine changes could appear verified against contaminated state (mixing pre-fix and post-fix action history), producing false-positive confidence in compliance logic correctness.

* **Separate large simulator-generated ML training corpus added, distinct from the locked 150-record demo/evaluation batch**
  * **Why:** ML risk/recovery-probability model (SoT §5, §9b.2) requires historical X/y examples to train on; the 150 Razorpay-shaped records are demo/evaluation data, not sufficient volume or outcome-labeled for training. A stochastic simulator (observable features + hidden variables: liquidity, issuer/bank condition, responsiveness) generates a larger synthetic corpus with genuine probabilistic outcomes, avoiding circular training (model must not learn a formula it was generated from). Public datasets (KKBox, UCI Credit Default, PaySim) referenced only as inspiration for realistic feature/probability design — not ingested as training rows, per the existing "self-generate all data" lock.
  * **What breaks if reversed:** Without this corpus, no valid train/test split exists — SoT §9b.2 proof requirement (precision/recall/confusion matrix, not just accuracy) cannot be met. Training directly on the 150-record demo batch would contaminate demo/evaluation data with training data, undermining "unseen test set" integrity.
  * **Scope boundary (explicit):** 150-record demo/evaluation batch stays unchanged and untouched. Core recovery-engine architecture (`classify()`, `decide_action()`, `execute_action()`) not modified. ML remains advisory signal only — rule engine stays final compliance authority (SoT §5, unchanged).

* **ML training target defined as `candidate_action`-conditioned recovery probability within a fixed 72-hour recovery horizon, not a general "will this case ever recover" label; `candidate_action` restricted to `retry`/`reminder`/`escalate` — `stop` excluded as a non-recovery action**
  * **Why:** A backward-looking or action-agnostic label would not answer the decision-relevant question ("if I take this specific eligible action now, how likely is recovery"). `stop` is a termination action with no recovery outcome to predict, so including it as a candidate would be meaningless.
  * **What breaks if reversed:** Model would predict a vague, non-actionable probability disconnected from the specific action the rule engine is about to take; `stop` as a candidate would require a fabricated/undefined recovery-probability semantics.

* **One training row generated per eligible `candidate_action` per simulated case (not one row per case); all rows from the same `case_id` are kept together in the same train/test split (grouped split, no leakage)**
  * **Why:** The model must learn `P(recovery | features, candidate_action)`, which requires multiple candidate-action rows per case sharing the same underlying (hidden) state. If same-case rows were split across train/test, the model could implicitly leak case-specific hidden-state information across the split boundary.
  * **What breaks if reversed:** Row-level (non-grouped) splitting would leak information between train/test for the same case, producing inflated/misleading validation metrics that don't reflect true generalization to unseen cases.

* **Simulator hidden variables (liquidity_state, issuer_availability, payment_method_health, customer_responsiveness, bank_condition_temp, recovery_willingness) sampled once per case and reused across all candidate_action rows for that case**
  * **Why:** Represents a correct causal "what-if" structure — the customer's true underlying state at a fixed moment is fixed; the simulator asks what would happen for each hypothetical action against that same fixed state, not a re-randomized state per action.
  * **What breaks if reversed:** Re-sampling hidden state per candidate_action row would break the "what-if comparison" semantics and make within-case candidate_action rows causally unrelated to each other, undermining the target definition above.

* **`retry_count` generation range in the simulator fixed from `rng.integers(0,3)` (bug — never produced retry_count=3) to `rng.integers(0,4)` (produces 0,1,2,3, including the true max-retries boundary state)**
  * **Why:** `retry_count==3` (retries exhausted, only reminder/escalate remain eligible) is a real, reachable state in the live rule engine. Excluding it from the training distribution left a blind spot exactly at the compliance boundary the model would need to score correctly in production.
  * **What breaks if reversed:** Model would have to extrapolate untrained for a state guaranteed to occur in live `decide_action()` calls, undermining prediction reliability exactly at the most compliance-sensitive boundary.

* **Two evidence-inspired (not dataset-fitted) calibration changes applied to the simulator: (A) added a boundary penalty in `retry_count_penalty()` specifically at `retry_count>=3`; (B) changed `customer_responsiveness` base generation from linear to a mild sigmoid-shaped non-linear function of `past_recovery_rate`**
  * **Why:** Public dataset research (UCI Credit Card Default, KKBox, PaySim) was reviewed to inform simulator realism per user instruction. UCI data showed default rate rises sharply at recent delinquency (motivates A) and that tree-based/non-linear models dramatically outperform linear models for repayment-risk prediction, implying real threshold/interaction structure (motivates B). PaySim was evaluated and explicitly rejected as a calibration source (fraud label, 0.13% positive rate, domain-mismatched). No source provided fitted numeric coefficients for our domain/schema — both changes' specific magnitudes are our own bounded design choices, explicitly commented in-code as such, not claimed as dataset-derived. Neither change was tuned to make XGBoost outperform Logistic Regression (verified: pre/post gap 0.0094→0.0095, effectively unchanged).
  * **What breaks if reversed:** Reverting removes the only externally-motivated (vs. purely arbitrary) calibration in the simulator, weakening the "AI judgment" answer if a judge asks how probability weights were chosen. Re-fitting exact coefficients from the public datasets without further explicit research/approval would misrepresent evidence-inspired design as dataset-derived calibration.
  * **Verification:** `verify_sensitivity.py` confirmed monotonic non-increasing retry effect for `candidate_action='retry'` (0.570→0.561→0.541 across retry_count 0,1,2) and expected downward trend with sharpest single-step drop at the retry_count=3 boundary for `reminder`/`escalate` (e.g. escalate: 0.633→0.625→0.617→0.594); no probability collapse to 0/1; XGBoost vs LR performance gap unchanged after calibration, confirming no favoritism toward either model.

* **`recovery_horizon_hours` (constant 72 in the training corpus) intentionally excluded from both `CATEGORICAL_FEATURES` and `NUMERIC_FEATURES` in training and inference**
  * **Why:** A constant column across all rows carries zero predictive signal; its only role is defining the outcome window used to generate `y` during simulation, not serving as a model input.
  * **What breaks if reversed:** Including a constant feature adds no information but risks confusing feature-importance interpretation and inference-time schema mismatches if the constant ever needs to change.

* **ML integration into `decide_action()` scores only the single candidate action the rule engine has already selected (`default_action` or `escalate`), not a comparison across `retry`/`reminder`/`escalate` alternatives for the same case**
  * **Why:** SoT §5 locks ML as advisory/predictive only; the rule engine is sole authority on action selection. Scoring only the already-chosen action keeps ML strictly post-hoc/advisory (an audit/reasoning signal), avoiding any path by which ML output could influence which action gets chosen.
  * **What breaks if reversed:** A multi-action comparison exposed to `decide_action()` would create a de facto channel for ML to influence action selection, breaching the locked "ML predicts → rule decides" boundary even if not implemented as an explicit override.

* **Production `retry_count` feature (fed to the ML model at inference) computed as a separate `retry_only_count` — count of `history` rows where `action_type=="retry"` AND `outcome=="executed"` — distinct from the existing compliance `contact_count` (which combines retry+reminder and remains unmodified, still driving the real `MAX_RETRIES` check)**
  * **Why:** The training corpus's `retry_count` feature specifically means actual retry actions only (it drives `eligible_candidate_actions()` and `retry_count_penalty()` in the simulator). Passing the compliance `contact_count` (a different, broader definition) as the ML feature would create a train/inference schema mismatch.
  * **What breaks if reversed:** Reusing `contact_count` for the ML feature would silently feed the model data that doesn't match what it was trained on, degrading prediction quality without any visible error.

* **Runtime `last_action_type` and `hours_since_last_action` ML features both derived from the same single most-recent `history` entry (not from two different history subsets)**
  * **Why:** Training data always pairs these two features from the same simulated event. An earlier draft sourced `hours_since_last_action` from `contact_history` (retry/reminder only) while sourcing `last_action_type` from full `history` — a potential inconsistency if the two sources ever disagreed, producing a self-contradictory row outside the training distribution.
  * **What breaks if reversed:** Reintroducing the two-source split risks feeding the model internally inconsistent feature pairs, an out-of-distribution input pattern never seen during training.

* **`recovery_actions.ml_recovery_probability` (REAL, nullable) added to the DB schema; persisted only on `outcome=="executed"` rows via `decision.get("ml_recovery_probability")`, defaulting to `NULL` on all blocked-outcome rows**
  * **Why:** The ML score computed in `decide_action()` was initially only present in the in-memory return dict with no persistence path — invisible to any audit trail, dashboard, or verification query. Schema needed extending for the signal to be inspectable/auditable, consistent with the "no silent actions, every decision logged" principle already governing the rest of `recovery_actions`.
  * **What breaks if reversed:** ML score becomes untraceable after each `decide_action()` call, unable to support future dashboard/audit-trail proof requirements (SoT §9b) or the Live Agent Console's reasoning panel (SoT §9a).
  * **Required follow-up:** Existing `recovery.db` files created before this schema change must be wiped and rebuilt via the fresh-DB protocol; `INSERT OR REPLACE`-based reloads do not retroactively add new nullable columns to an already-created table.

* **Stage 3 LLM confidence threshold locked at 0.6; new `flagged_manual_review` outcome added to the locked reason-code list; new schema columns `recovery_actions.flag_type`, `messages.intent_confidence`, `messages.mentioned_reason` added**
  * **Why:** SoT §9c-1 originally left the threshold as an example ("e.g. <0.6"), not a locked value. Confidence gating and mismatch detection required a genuine hard-stop path (not an advisory-only flag) to make manual review a real control boundary rather than decorative metadata — `execute_action()` needed a way to represent "no action was taken" distinct from every existing outcome, and the decision needed a place to record *why* a case was flagged.
  * **What breaks if reversed:** Removing the hard-stop collapses manual-review into a no-op flag, reintroducing the exact "LLM influences control decisions" risk Section 5 was designed to prevent; removing `flag_type` loses the audit distinction between a genuine mismatch and a legitimate root-cause update.

* **`root_cause` deliberately excluded from the Gemini prompt in `parse_intent.py`; `mentioned_reason` is derived purely from customer-stated language, with the root-cause comparison performed entirely in Python inside `decide_action()` after both values independently exist**
  * **Why:** Sending the stored `root_cause` to the LLM risked anchoring bias — the model could unconsciously echo back the system's existing belief rather than independently extracting what the customer actually said, defeating the purpose of an independent mismatch check.
  * **What breaks if reversed:** Reintroducing `root_cause` into the prompt would make `mentioned_reason` a biased confirmation signal rather than an independent cross-check, undermining the entire self-consistency/mismatch-check differentiator (see earlier locked decision on this).

* **Intent/root-cause compatibility check implemented as explicit logic (`_check_intent_compatibility()`), not simplistic equality — `payment_method_updated` paired with a method-class root cause (`expired_card`, `payment_declined`, `authentication_failed`) is treated as a legitimate root-cause update (`root_cause_update_candidate`, non-blocking), while the same intent paired with a non-method-class root cause (`insufficient_funds`, `gateway_timeout`, `network_error`) or any other intent mismatch is treated as a genuine conflict (`mismatch`, blocking)**
  * **Why:** A customer updating their card/payment method genuinely resolves method-class failure reasons — treating this as a "conflict" would incorrectly hard-stop cases that are actually being legitimately resolved, defeating the purpose of the mismatch check rather than serving it.
  * **What breaks if reversed:** Reverting to simple equality would incorrectly route every `payment_method_updated` reply to manual review whenever the customer doesn't restate the exact stored root cause, even when the update is the correct resolution — inflating false-positive manual-review volume and undermining trust in the flagging mechanism.

* **`GEMINI_MODEL` changed from `gemini-1.5-flash` to `gemini-3.6-flash`; `GEMINI_TIMEOUT_SECONDS` changed from 15 to 30, in both `parse_intent.py` and `generate_message.py`**
  * **Why:** Live debugging discovered `gemini-1.5-flash` is no longer available for this API key/account (`404 NotFound`, then a further `404` on the interim replacement `gemini-2.5-flash`, with Google's own error message pointing to `gemini-3.6-flash` as current). Separately, the original 15s timeout produced a real `DeadlineExceeded` under actual `system_instruction` + structured-JSON-generation latency on this model, not a config/auth issue.
  * **What breaks if reversed:** Reverting the model name causes every live Gemini call to fail immediately (confirmed via traceback), silently falling back to the safe-but-non-functional fallback path on 100% of calls; reverting the timeout reintroduces the same deadline failure under normal latency, degrading the live/"ok" success rate for no functional reason.

* **`handle_customer_reply()` persists the customer's message as its own atomic commit *before* calling `decide_action()`/`execute_action()`; if that insert fails, the function aborts immediately and does not proceed to the engine — accepted as a deliberate fail-closed design over wrapping the whole flow in one externally-managed transaction**
  * **Why:** `execute_action()` already commits internally as part of its existing, unmodified "every call logs a row" contract (a prior architectural lock); wrapping it inside a larger transaction would require modifying `execute_action()`, which was explicitly out of scope. Given that constraint, persisting the customer's message first and treating it as its own durable unit is the safest achievable design — proceeding to `decide_action()` without a persisted message would let compliance checks (`_has_customer_reply`) reference a reply that technically doesn't exist yet in the DB.
  * **What breaks if reversed:** Full cross-table atomicity was evaluated and rejected as infeasible without changing `execute_action()`'s existing commit behavior; the accepted residual gap (a message can exist with no corresponding `recovery_actions` row if `classify`/`decide_action` fails unexpectedly after message insert) is documented and considered safe-by-default (fail closed, `recovery_status` untouched) rather than hidden.

* **`generate_recovery_message()` is a pure function (no DB reads/writes) and is only ever intended for `action_type in {"retry","reminder"}`; deterministic non-LLM fallback templates are root-cause-specific for `retry` (6 templates, one per locked `error_reason`) and event-type-specific for `reminder` (`checkout_abandoned`/`invoice_overdue`, never inventing a root cause since it's always null for these event types)**
  * **Why:** `escalate` is internal routing and `stop` means contact has ended — generating a customer-facing message for either would contradict the rule engine's own decision. Deterministic fallbacks needed to preserve the same domain-specificity as the LLM path even when Gemini is unavailable, per explicit user correction rejecting a single generic fallback string.
  * **What breaks if reversed:** A generic fallback (rejected alternative) would degrade message quality/specificity silently whenever Gemini fails, with no way to distinguish "system down" from "system working as intended" from the customer's perspective; allowing message generation for `escalate`/`stop` would create customer-facing communication about actions that are supposed to be either internal or terminal.

* **`deliver_recovery_message()` eligibility gate restricted to exactly `outcome=="executed"` AND `action_type in {"retry","reminder"}`; `escalate`, `stop`, every `blocked_*` outcome, and `flagged_manual_review` are all explicitly skipped (`status="skipped_ineligible"`, zero DB writes) — wired into both `core_loop.py` (batch) and `handle_customer_reply.py` (reply-triggered) via one added call each, immediately after their existing `execute_action()` call**
  * **Why:** Batch-generated messages from eligible actions are explicitly part of the real recovery/audit flow (not test-only), per direct user clarification — both entry points must behave identically rather than only wiring the reply-triggered path. Restricting eligibility strictly to already-executed customer-contact actions preserves `decide_action()` as sole authority: message generation can only ever phrase a decision already finalized, never influence one.

The project is synthetic end to end by design, with no external integration now or ever, so the gap was always ours to close. Phase 5 closed it by *generating* the channel and the health series through the Data Factory's own generator, which is the opposite of fabricating a plausible value at read time. The "never invent an input" rule the entry states is intact and was the constraint the fix was built to satisfy.

## PHASE 5 — RULE ENGINE & BOUNDED EXECUTOR

* **`blocked_max_retries` removed from `DECISION_OUTCOMES` — the closed compliance vocabulary drops from 7 values to 6**
  * **Why:** it had **no producer in any commit in the project's history**. Checked at every revision (`294f517`, `b512628`, `e690789`, `078ca79`, `7c9fc24`, `866e478`): `emits=0, mentions=1`, the single mention being `decide_action()`'s own docstring. At the first commit the max-retries branch already returned `action_type="stop", outcome="executed"`, identical to today. This is the enactment in code of the ruling already recorded above at "outcome field standardized to a fixed reason-code set" — that entry declared the value dropped, but `db.py` and `EXECUTION_PLAN.md:103` still listed it, so the declaration and the code disagreed for the whole project until now.
  * **What breaks if reversed:** adding a real `blocked_max_retries` branch is a live regression, not a clarification. By the `allowed == (outcome == "executed")` invariant, such a branch must carry `allowed=False`; `execute_action()` then skips its executed block entirely, so no execution row is written, **the opportunity is never closed**, and `core_loop` re-selects it every cycle (`status IN ('open','recovering')`, `contact_count` still ≥ `MAX_RETRIES`) and re-emits the same outcome indefinitely. Semantically the prefix is also wrong: the other five `blocked_*` codes mean "not now, the opportunity stays open, try later", whereas max-retries means "never again, the case is closed". Filing a permanent termination under the same prefix makes the vocabulary less auditable, not more.

* **Network health at serving time — CLOSED. `payments` gains `bank`/`psp`, the seed set gains a generated health series, and `optimize.py` reads the real channel**
  * **Why:** see the superseded Phase 4 entry above for the original (mistaken) premise. Vocabularies and the series generator are **imported** from `data_factory` (`entities.BANKS`/`PSPS`, `bank_health_timeseries.generate_series_for_channel`, the `baseline` calibration profile), never reimplemented, so a seeded payment names the same channels, drawn the same way, as the rows the model trained on. Verified live: `network_health_known` moves from `0.0` to `1.0` across all 92 seeded opportunities, with rolling health spanning `[0.5425, 0.9846]` over 53 distinct values.
  * **What breaks if reversed:** the four network-health features go dead again and the model silently runs in a regime that discards a real signal. Note the seed change is **strictly additive** and must stay so: channel selection and health generation draw from a dedicated generator (`CHANNEL_RNG_SEED`), never the main `rng`. A first attempt drew from the main stream, which shifted every subsequent draw and silently regenerated the *entire* seed set — surfacing as a new failure in `test_do_nothing_legitimately_wins_at_least_one_real_ranking` because the underlying cases had changed. "Adding a field" quietly changing every other field is exactly what a seed generator can hide.

* **The unix → simulated-hour mapping is Option A (modulo), not a clamped-linear or real-time-anchored map: `sim_hour = WINDOW + ((now − ORIGIN)/3600) mod (HORIZON − WINDOW)`, horizon 720h**
  * **Why the alternatives were rejected — this is the reasoning that must survive, not the formula:** the lookup is **not honest past the end of its series**. For an `as_of` beyond the last window, `outcome_features.py:262` clamps (`lo > hi` → `lo = hi`) and returns the single final 4h observation **with `known=True`, forever**. Every opportunity then reads an identical constant while the feature asserts the data is real — strictly worse than `known=0`, because a constant claiming to be real is indistinguishable from data the model can learn from. A **clamped-linear** map reaches that state on a date, silently, once wall-clock passes `ORIGIN + horizon`. A **real-time-anchored** series reaches it too, by staleness, on a schedule nobody is tracking. Modulo structurally cannot: it always lands inside the series. The offset by `WINDOW` and the reduced span keep the result inside `[WINDOW, HORIZON)`, exactly the range where the lookup is truthful — below `WINDOW` no observation has closed (`known=False`, honest), at or past `HORIZON` the clamp takes over. Verified over 200k timestamps including pre-origin ones. The accepted cost is a wrap discontinuity and a false periodicity at the horizon's period: bounded and visible, against a failure mode that is neither.
  * **What breaks if reversed:** any mapping that can run off the end of the series inherits the silent-constant failure. Separately, the horizon must stay **materially larger** than `NETWORK_HEALTH_WINDOW_HOURS` (168.0), the trailing-average span: at horizon == trailing span every query averages from window 0 and the rolling value degenerates into a prefix average. Measured rolling-score spread by horizon — 168h: 0.0864, 720h: 0.1572, 2880h: 0.2119. 720h was chosen over the Data Factory's 2880h default on measured cost, not preference: seed generation 1285ms vs 347ms, and the full pytest suite exceeded 20 minutes at 2880h against a 204s baseline, because the seed set regenerates once per test.

* **`optimize.py` unfrozen for exactly three lines, for network-health wiring only — a dated, narrow exception to the frozen-input list**
  * **Why it is narrow rather than a scoring change, verified rather than asserted:** `bank`, `psp` and `decision_time_hours` are **not model features** — none appears in `outcome_features.ALL_FEATURES` (26 entries). They are lookup keys only, so the change can reach the model through exactly four features (`network_health_score_rolling`, `..._success_rate_rolling`, `..._timeout_rate_rolling`, `network_health_known`) and through nothing else. Candidate generation, scoring, EIV arithmetic, ranking and persistence are untouched. `test_the_frozen_exception_stayed_narrow` fails if any of the three ever becomes a model feature, because that is the premise the exception rests on and it must not be silently inheritable.
  * **What breaks if reversed:** reverting the three lines returns every live scoring to `network_health_known = 0`. More importantly, **this exception does not authorise any further change to `optimize.py`** — it was granted for one purpose, is now closed, and any other modification needs its own ruling.

* **C1 — the retracted ranking-correctness test was RE-IMPLEMENTED, not retired**
  * **Why the original was wrong:** it compared across measurement spaces — `truth = analytic_p(a) − analytic_p(b)` (probability) against `model = incremental_amount(a) − incremental_amount(b)` (rupees) — on hand-constructed contexts. Those orderings are *permitted* to disagree, because `E[amount|recovered]` varies per candidate (the ~16% rupee-space pair-order sensitivity). Phase 4 §8.2 had already isolated the fault exactly: same contexts, same ground truth, **0.958 in probability space vs 0.812 in rupee space**. The comparison axis was the bug, not the ground truth.
  * **Why the replacement is trustworthy:** it implements `locked_thresholds.json / phase3_temporal / ranking_pair_definition` **verbatim** — a definition locked `2026-08-30T15:32:43Z`, before Phase 4 began and long before this measurement was conceived, so the bar cannot have been chosen for the result. Pairing and effect computation are **reused** from `evaluate_outcome_model.compute_effects()`, the same function the trusted `phase3_temporal` gate calls, so the two gates cannot drift into measuring different things while both claiming to measure ranking correctness. Measured on frozen held-out data: temporal 0.8886 / calibration 0.8966 at the locked 0.05 floor (bar 0.85), and 0.9511 / 0.9489 at G7's 0.12 floor (bar 0.90).
  * **What breaks if reversed:** a single-floor assertion re-opens the threshold question. Agreement rises monotonically with the effect floor (0.889 → 0.928 → 0.951 → 0.991 at floors 0.05/0.08/0.12/0.20), so **a bar is only meaningful alongside the floor it was set at** — the old test's 0.90 was borrowed, by its own comment, from `ground_truth_treatment_effect`, a bucket-level measurement, not pairwise within-case ranking. Asserting at both operating points is what makes the choice of bar irrelevant. A third test pins the monotonicity itself: if agreement ever fell as the generator separated pairs *more* decisively, the measurement would be suspect.

* **C2 retracted — and this is the SECOND occurrence of the same error class, after Phase 4's G7 retraction**
  * **The finding, and why it was wrong:** the joint model appeared to have learned the wrong sign for `payment_history_score`, inverted in 75–99% of cases across four conditions, against a generator that is monotonically positive in it (`d(z)/d(phs) = +0.7`). It was not a model defect. The diagnostic probe swung the feature `0.05 → 0.95`; the training corpus spans `[0.2031, 0.9236]` and contains **zero rows** outside that. Partial dependence shows a flat leaf below the training minimum and a −0.063 cliff at 0.95 — and that cliff *is* the −0.063 originally reported. Within the interquartile range the model is directionally correct on **92/92** opportunities (+0.039 mean), and its in-support magnitude (+0.0229 across p10–p90) matches the corpus (+0.0221). Generation, preprocessing, correlation and the training script were all cleared first.
  * **Why this belongs here and not only in one phase's notes:** it is the **second** time a conclusion was drawn from inputs the model was never fit on. Phase 4's G7 retraction was the first — constructed contexts, cross-space comparison. Two independent investigations, two false findings, one root cause: *evaluating a model outside the support of its training data measures leaf placement, not a learned relationship.* A pattern that recurs across phases needs to be visible across phases.
  * **What breaks if reversed:** the mechanical guard is that any single-feature directional probe must report the feature's training-support range alongside its result and swing within it. `test_everything.py` enforces this structurally through `TRAINING_SUPPORT` plus a check that re-derives those bounds from the training corpus, so they cannot go stale. Removing that guard makes a third occurrence likely.

* **Two concurrency defects fixed: compare-and-swap on recovery confirmation, and an atomic read-decide-write for contact actions**
  * **Why compare-and-swap:** `mark_opportunity_recovered()` read `status`, checked it, then issued an `UPDATE` with **no status precondition**. Every concurrent caller passed the check, every one updated, every one was returned `{"status": "ok"}` — while the row ended up perfectly clean with a single `recovered` status. Measured, 40 trials × 8 barrier-released callers: **252 of 320 calls told "ok", exactly-one-winner held in 0/40 trials**; after, 40 of 320, holding 40/40. In both cases the database ends identical — only the return values differ, which is precisely how one recovery gets counted N times by any ledger that trusts them.
  * **Why an explicit lock for contact actions:** `decide_action()` enforces cooldown by *reading* prior decisions, so two overlapping workers could both read "no recent contact" and both fire. Cooldown was never wrong; it simply was not atomic. `engine/opportunity_lock.py` wraps the read-decide-write in one `BEGIN IMMEDIATE`, so the second worker blocks at the BEGIN rather than proceeding on a stale read. Measured, 25 trials × 4 workers: **91 contacts fired against a safe minimum of 25 (25/25 trials double-contacting)**; after, exactly 25, 0/25. It deliberately adds **no compliance logic** — re-checking cooldown inside the lock would be a second component enforcing the same rule, the authority drift the invariants forbid. `PRAGMA busy_timeout = 5000` was required alongside it: SQLite's default is zero, so the second writer would fail instantly with "database is locked" — a worse failure than the one being fixed.
  * **Why `trigger_event.py` was excluded:** it does not share the race. It mints a fresh `opportunity_id` per call, so concurrent calls touch different rows, and duplicate delivery of one upstream event is already guarded by the `UNIQUE` index on `ingestion_event_id` plus an `IntegrityError` handler that resolves to the winner — the same compare-and-swap shape the recovery path was missing.
  * **What breaks if reversed, and the lesson worth carrying:** **both pre-existing tests passed in isolation the entire time both bugs were live.** `test_two_overlapping_batch_cycles_do_not_double_act_on_one_case` passed **12/12** standalone while the race was fully reproducible, because its two `run_cycle()` calls each iterate ~92 opportunities sequentially and rarely collide on the same one; and `test_concurrent_recovery_confirmations_produce_one_winner` states in its own docstring "may pass by luck; a failure is conclusive". A green concurrency test is weak evidence by construction. Direct, barrier-forced measurement of the mechanism is what establishes the behaviour — future phases should not treat a passing race test as proof of safety.

* **W6 — the scheduled dispatcher advances execution rows by compare-and-swap and never re-executes; three defects found while planning it were fixed first**
  * **Why the dispatcher may only UPDATE:** `execute_action()` is not idempotent at the call level — calling it twice with one decision mints two decisions and two executions, because each call inserts a fresh decision row for the execution to hang off, which the `UNIQUE` index on `recovery_executions.decision_id` cannot prevent. So `dispatch_scheduled.py` never calls it and never INSERTs; its entire write surface is `UPDATE ... WHERE execution_id = ? AND state = ?`, where `rowcount == 1` means this sweep won the row and `0` means it must do nothing at all. **That predicate, not the index, is what makes duplicate dispatch safe** — the index prevents a second execution *row*, but only the compare-and-swap prevents a second *message to the customer*. Both properties are enforced by static tests rather than convention. Evidence: sequential double sweep leaves decisions 1→1→1 and executions 1→1→1 with one agent message; 25 barrier-forced trials × 2 concurrent sweeps on one due row give exactly 1 dispatch and 1 message every time; and the negative control with the predicate removed produces **2** messages, so the tests demonstrably detect the failure they claim to prevent.
  * **Why the optimizer is absent rather than merely outside the lock:** the dispatcher fires an action that was ranked and authorised at schedule time, so re-ranking at dispatch would be re-deciding — it decides *when*, never *whether* (EXECUTION_PLAN.md:83). A consequence is that the measured ~650ms `optimize_opportunity()` call structurally cannot land inside `opportunity_lock`'s ~6ms hold. `OPTIMIZER_ENABLED_BY_ENTRY_POINT["dispatch"]` is therefore inert by design, not by oversight.
  * **At-most-once, chosen deliberately:** the sweep selects only `state='scheduled'`, so a row left in `dispatched` — process death, or a delivery exception — is never retried. A claimed row may already have reached the customer, so an automatic retry *is* the duplicate contact the design exists to prevent. Failing to send is recoverable by a human; sending twice is not. `stuck_dispatches()` enumerates them, and the absence of any alerting around it is recorded as an open obligation rather than left implicit.
  * **What breaks if reversed:** implementing dispatch by re-calling `execute_action()` makes an idempotency key on the decision mandatory, and the gate cannot be met without one. Dropping the `AND state = ?` predicate reproduces the double contact directly — measured, 2 messages.

* **Cooldown now counts delivered contacts, not approved decisions — a dated amendment to `decide_action()`, and the golden corpus cannot police it**
  * **Why:** `execute_action()` writes an `outcome='executed'` decision at *schedule* time, before anything is sent, and cooldown read exactly that predicate. Measured before the fix: a 4h-scheduled reminder revalidated at its due time returned `Cooldown active. 20.0h remaining before next contact allowed.` — the scheduling decision blocking the action it scheduled, making the `4h` timing structurally undispatchable — and three unfired scheduled reminders returned `Max 3 contact attempts reached`, consuming the customer's whole contact budget before any contact happened.
  * **Why it is phrased as an exclusion, which is the entire design:** counting only decisions whose execution reached `executed` would silently stop counting every pre-Phase-5 row, since the golden corpus inserts decision rows with no execution row at all. So a decision counts as contact **unless** its execution row exists and names a not-yet-delivered state. Absence of evidence is treated as contact made — the safe direction for a compliance rule. No threshold moved: cooldown is still 24h, the ceiling still 3.
  * **The limit of the backward-compatibility proof, stated because it is easy to overclaim:** the corpus reproduces at 0 differing fields, but a negative control running the *inverted* predicate **also** passed the corpus 5/5 while failing four directional tests — no corpus scenario carries an execution row, so the corpus is blind to this class of change in both directions. Corpus identity proves the amendment disturbs nothing pre-existing; it does **not** prove the amendment correct. That proof is `tests/test_phase5_revalidation.py`, shown sensitive in both directions by the same control.
  * **What breaks if reversed:** the `4h` timing becomes undispatchable again and three queued actions exhaust the ceiling before any is sent. Note the amendment was scoped to cooldown and the ceiling only: `retry_only_count`, `last_action_type` and `hours_since_last_action` are ML features and still count unfired actions — flagged for a ruling, not silently extended, because changing model inputs is a scoring change.

* **`decide_action()` gains an `as_of` evaluation clock, because dispatch-time revalidation was closing nothing**
  * **Why the W2 flag did not do what it said:** `DISPATCH_REVALIDATES_VIA_DECIDE_ACTION` was declared to stop a 3-day-scheduled action firing at 3am, but both contact-window implementations read the local hour of the opportunity's `created_at`, which is identical at schedule time and due time. Revalidating therefore returned the same verdict it gave when scheduling, and the 9pm–8am ban was unenforceable for every scheduled action. The flag's stated mechanism was wrong; it is corrected in place in `phase5_config.py` rather than quietly reinterpreted.
  * **Why this is a real violation and not a theoretical one:** W6 is the component that makes scheduled firing reachable at all, so shipping the dispatcher without this ships the violation. Same severity tier as the two concurrency defects fixed earlier in this phase.
  * **What breaks if reversed:** with `as_of` None the expression is byte-for-byte the pre-amendment one, which is what the corpus pins — so the default path is safe, and only a caller that passes a clock sees the new behaviour. The amendment bit immediately in a useful way: the first run of the dispatch suite at 23:00 local failed *every* scheduling test because every due action was correctly cancelled as `blocked_contact_hours`. The tests were wall-clock-dependent, not the code; they now pin `now`, the counterpart of the suite's existing `recent_in_window_ts()`.

* **Message delivery is gated on execution state, not on the compliance outcome — the customer was being contacted at schedule time**
  * **Why:** `deliver_recovery_message()` gated on `outcome == 'executed'`, but `outcome` is a *compliance* verdict written the moment an action is approved, while whether it fired lives in `recovery_executions.state`. For a scheduled action the two disagree for the whole window. Measured before the fix: `delivered=True`, 1 agent message written, while the execution row read `state='scheduled', executed_at=None`, four hours before it was due — and the dispatcher would have sent a second. After: 0. **Reading a lifecycle answer out of the compliance field is precisely the conflation the "Execution separation" gate and the five-distinct-concepts invariant forbid**, which is why this was fixed in W6 rather than deferred to W7 as new-feature scope.
  * **What breaks if reversed:** the double contact returns the moment anything is scheduled. Delivery now **fails closed** when the caller cannot name its execution — a missed message is visible in the returned status and costs one delayed follow-up, whereas a duplicate contact is not recoverable — and all three entry points are pinned structurally to pass `decision_id`, so W7's unification cannot drop it on the way.

* **W7 — one shared `run_recovery_pipeline()` for all three entry points, with the classify divergence resolved toward the opportunity's stored root_cause**
  * **Why the shared function, and why structurally verified:** the gate requires "a single shared function is called by all three entry points", not merely matching output, so a future change to one cannot silently diverge from the others. That the requirement was justified is evidenced by the fact that the three **had already diverged** before W7: they disagreed about what feeds `classify()`'s `error_reason` (core_loop the latest payment's, handle_customer_reply the opportunity's, trigger_event its argument). The divergence was introduced by the Phase 1 schema split (`7c9fc24`) — before it, both loop entry points called the identical `classify(payment)` (`e690789`) — and no decision entry, phase-notes document or commit message ever ruled on it.
  * **Why `opportunity.root_cause` won, reversing the initial recommendation:** `classification["root_cause"]` is a **compliance input** on the reply path. `decide_action.py`'s intent-mismatch gate fires only when intent arguments are supplied — only `handle_customer_reply` supplies them — compares `classification["root_cause"]` against the LLM's `mentioned_reason`, and on conflict returns `allowed=False` / `flagged_manual_review`. The gate's own message says "Extracted intent conflicts with **stored root_cause**", wording that predates the schema split. Feeding it a per-attempt field would have it judge a customer's claim against something other than the case's diagnosis. On `core_loop` that gate never fires, so there the field is ML input and phrasing only — which is exactly what that module's docstring already claimed. Both prior behaviours were locally correct; only one is correct once they must be the same. `latest_payment.error_reason` is retained as a NULL-fallback.
  * **The change is behaviourally identical, and structurally so:** across all 150 seeded opportunities (64 `payment_failed`, 17 multi-attempt, 0 without a payment row) zero have a latest-payment `error_reason` differing from their `root_cause` — because the only two writers of a payments row (`generate_seed_data.py:322`, `trigger_event.py:198`) both set it from the opportunity's own root cause. Parity was measured in one process against two freshly-seeded databases with `time.time()` pinned, so timestamps, autoincrement ids and `ml_recovery_probability` were compared directly rather than normalised away: **92 batch opportunities, 6 trigger_event specs, 5 reply pairs — 0 differing at tolerance 0**, with the reply set covering the blocking branches (`flagged_manual_review`), and the `recovery_decisions` / `recovery_executions` / `messages` tables identical row for row.
  * **What breaks if reversed:** three entry points drift again, and the next divergence will be as invisible as this one was for four phases. Note the asymmetries that must NOT be tidied away: `trigger_event` still does not take `opportunity_lock` (it mints a fresh opportunity_id per call and is already guarded by the `UNIQUE` index on `ingestion_event_id`), and the dispatcher is deliberately **not** a caller because it must never call `execute_action()`. Both are now declared tables with import-time raises rather than conventions.

* **The optimizer's position outside the lock is now measured in the unified pipeline, not just asserted structurally**
  * **Why measuring beats a source check:** a structural "no `optimize_opportunity(` inside the `with` block" test can be satisfied by code that still pays the cost some other way. The sharp form is to measure the hold in both states. With the optimizer ON, total pipeline time rises ~27x (p50 29.54 ms → 796.39 ms) while the **lock hold stays flat** (p50 25.21 ms → 23.85 ms, p95 30.57 ms → 25.92 ms) against a ceiling of 50.0 ms committed to `phase5_config.py` before the measurement ran. The pre-W7 sequence measures p50 28.06 ms on the same machine, so unification itself did not change the hold.
  * **What breaks if reversed:** putting ranking back inside takes the hold to ~650 ms, which against `db.BUSY_TIMEOUT_MS = 5000` is the difference between ~850 workers able to queue and about 7.

* **NEW DISCLOSURE — the first lock hold in any process is ~780 ms, because the ML model loads lazily inside it (closeout C4)**
  * **Why this is the same class of defect the optimizer was banned for:** `decide_action()` calls `_load_ml_model()` lazily, and the first call in a process happens inside `decide_action()`, which runs INSIDE `opportunity_lock`. Measured from a cold process over 8 consecutive opportunities: hold #1 **779.35 ms**, then 9.75 / 6.23 / 6.00 / 7.23 / 6.46 / 5.89 / 6.41 ms — a **121.5x** spike, with the warm holds matching the 5.88 ms p50 `opportunity_lock.py` records. Against `BUSY_TIMEOUT_MS` that puts the first cycle after every restart in the regime where roughly the seventh concurrent worker fails with "database is locked".
  * **Why it is disclosed and not fixed here:** it predates W7 (the pre-W7 sequence shows p95 946 ms before the model warms) and the fix — warming the model before the lock, or loading at import — changes when a frozen-adjacent module reads its artifact, which needs its own ruling. Pinned by a test that asserts the *limitation*, the same pattern used for `execute_action()`'s call-level non-idempotency, and which skips with a printed reason when the model is already resident.
  * **What breaks if reversed:** removing the pin lets a genuine 780 ms write-lock hold pass unnoticed as normal startup cost.

* **A locked bound's stated safety margin was corrected after measurement, without moving the bound**
  * **Why:** `UNIFIED_LOCK_HOLD_P95_CEILING_MS = 50.0` was derived and committed before the measurement, justified as "~8x above the recorded p95". That derivation compared against a **bare-process** figure (5.88 / 6.24 ms), while the test that checks the ceiling runs inside a loaded pytest session where the same warm hold measures **24–32 ms**. The true margin against a false failure is about **1.6x, not 8x**.
  * **What was done about it:** the value was **not changed**. Moving a bound in either direction after seeing the results it governs is exactly what the standing rules forbid, and it still detects the regression it exists for by ~25x (a ~650–800 ms hold against a 50 ms bar). The comment was corrected in place, dated, so the false claim of headroom does not stand.
  * **What breaks if reversed:** silently raising the ceiling to restore comfort would convert a disclosed thin margin into an undisclosed one. If it ever flakes, the correct response is a dated amendment with a diagnosed reason independent of the failing run.

* **Document drift found and resolved: `SoT.md` ↔ `EXECUTION_PLAN.md` on method_change, and `EXECUTION_PLAN.md` ↔ this file on `blocked_max_retries`**
  * **Why the two were resolved in opposite directions:** for method_change, `SoT.md:63` listed "alternate payment method" among the rule engine's dispatchable tools while `EXECUTION_PLAN.md:206` says the executor "structurally excludes autonomous payment-method switching". EXECUTION_PLAN governs — it is the later, more specific statement, reinforced by a permanent invariant — so `SoT.md:63` was amended (one line, in a 205-line file, nothing else moved). For `blocked_max_retries` the precedent **inverts**: here *this file* is the later, more specific record (a decision entry with a recorded rationale and a "what breaks if reversed" clause) and `EXECUTION_PLAN.md:103` is a general schema table, so `EXECUTION_PLAN.md` was amended instead. The rule is "the later, more specific record governs", not "EXECUTION_PLAN always wins" — applying the first resolution as a precedent to the second would have produced the wrong answer.
  * **What breaks if reversed:** a reader consulting only one document reaches a different conclusion about what the system does. Note `SoT.md:59` (Section 3.5, Optimize) was deliberately **left alone** — "Rank every eligible (action, timing, payment-method) combination" is *correct*; the optimizer genuinely does rank payment-method combinations. The drift was only ever about what the executor may dispatch, and editing that line would have introduced a new error while fixing an old one. Note also that this file's own enumeration at the "fixed reason-code set" entry is itself partially stale: it names five values and omits `flagged_manual_review`, added later by the Stage 3 LLM confidence gate. Its *ruling* stands; its *list* does not.

# PHASE 6 — LIVE EXPERIMENT ASSIGNMENT & OUTCOME OBSERVATION (2026-09-04)

* **Randomization is hash bucketing (R2), not stratification (R4) — and the independence argument is structural, not empirical**
  * **Why:** `blake2b(salt + opportunity_id)` read as a uniform draw. `opportunity_id` is `uuid4().hex[:12]`, minted before any covariate is read, so hashing it *cannot* induce a correlation with amount, root cause, customer or timing — the argument does not depend on a balance test coming back clean. It is also reproducible (any row's arm recomputable from id + committed salt, years later, without the database), stateless (correct under concurrency, unlike a seeded RNG sequence whose result depends on call order) and idempotent (a retry cannot re-randomize a live opportunity).
  * **What breaks if reversed:** a `SystemRandom` draw would be equally random and completely unauditable — no row's assignment could ever be re-derived or disputed. A seeded `random.Random` sequence would be reproducible only if call order were identical, which two concurrent workers cannot guarantee.

* **Assignment is at opportunity-creation time, in the entry point, and nowhere else**
  * **Why:** `trigger_event.py` is the only `INSERT INTO opportunities` in the engine. The call sits after the commit (so the FK is satisfiable and no assignment is orphaned), before the pipeline (so the first decision already sees the arm), and after both duplicate-event short-circuits (so a replayed upstream delivery cannot re-randomize). It stays in the entry point rather than the shared pipeline for the reason W7 recorded: an entry point's own creation work stays with it, only the recovery pipeline is shared.
  * **What breaks if reversed:** assigning after the pipeline produces a control-arm row carrying a treatment in its history — an inconsistency nothing downstream can repair, and one that looks perfectly well-formed in the data.

* **Control suppression lives in `decide_action()`, not in the pipeline — and that choice is what makes it real rather than cosmetic**
  * **Why:** `decide_action()` is the sole authority that can set `allowed: True`, and it is the single choke point *both* live paths already traverse: `run_recovery_pipeline()` for all three entry points, and `dispatch_scheduled._still_permitted()` for the dispatcher, **which does not go through the pipeline**. A check in `pipeline.py` would have left the dispatcher open, so an action scheduled before assignment could still fire after it. Because the gate is in the rule engine, `dispatch_scheduled.py` needed no change at all. It is the *first* statement of the hardcoded body, so suppression is not a property of branch ordering, and it returns before `_load_ml_model()`.
  * **What breaks if reversed:** the counterfactual gate would still pass on the pipeline paths while the dispatcher quietly fired treatments at the control arm — the exact failure mode the gate exists to catch, invisible to it.

* **A suppressed control opportunity writes a decision row (`suppressed_holdout`), it does not return silently**
  * **Why:** the permanent invariant is that every action the system takes *or declines to take* is logged with a reason. It also gives the counterfactual gate something affirmative to inspect: "control has 1723 decisions, all suppressions" is far stronger evidence than "control has no executed decisions", which a system doing nothing at all would also satisfy. Reusing `flagged_manual_review` was rejected outright — it means "a human should decide" and would have injected the entire control arm into the manual-review queue.
  * **What breaks if reversed:** suppression that logs nothing is indistinguishable from suppression that never ran.

* **An opportunity with no assignment row is NOT in the experiment and is NOT suppressed — the project's one deliberate fail-open**
  * **Why:** failing closed here would freeze all 150 pre-Phase-6 seeded opportunities, none of which was ever randomized. That is not conservative; it would silently disable the entire demonstration world in the name of an experiment those rows are not part of. Recorded as a dated exception rather than left looking like an oversight, and it is what makes the W1 golden corpus reproduce unchanged.
  * **What breaks if reversed:** defaulting unassigned rows to `treatment` would enrol a never-randomized population into the treatment arm and inflate every incremental number Phase 7 computes.

* **`observe_outcome()` is the single ingestion path, and unifying on it FIXED a divergence rather than merely centralising one**
  * **Why:** there were two live writers of the business-outcome columns and they had already drifted — `mark_opportunity_recovered()` guarded its write with a compare-and-swap against a concurrent terminal transition, `execute_action()`'s terminal `stop` branch did not. A stop racing a recovery could therefore overwrite a recovered case as unrecovered, corrupting exactly the numerator Phase 7 divides by. Unification adopted the *guarded* implementation unchanged rather than averaging the two. `mark_opportunity_recovered` survives as a thin, clearly-labelled operational utility, as the plan requires, with its legacy return shape preserved exactly.
  * **What breaks if reversed:** a second write route resolving opportunities under different rules biases the cross-arm comparison in a way nothing downstream can detect, because the resulting rows look perfectly well-formed.

* **`observe_outcome()` is deliberately NOT experiment-aware, enforced by a static gate**
  * **Why:** a control opportunity can and must be able to recover — that is the entire point of a control arm. An outcome writer that consulted `experiment_assignment` could suppress control recoveries and drive the measured incremental effect to whatever number the system wanted, making the experiment circular.
  * **What breaks if reversed:** the incremental figure becomes unfalsifiable.

* **`MIN_ASSIGNED_N` amended 200 → 3500 after the balance gate failed — and `MAX_ABS_SMD` was NOT touched**
  * **Why:** the gate failed at n=240 with max |SMD| = 0.386. Rather than move the bound, the question asked was whether the gate is *passable* at that n. Measured against the known-correct randomizer, seeded and reproducible: a perfect randomizer fails it **99.67% of the time at n=240** (2 of 600 trials pass). The cause is analytic and independent of the failing result — SE(SMD) ≈ 2/√n, so each level's SMD has SD ≈ 0.13 there while the gate takes the maximum over ten such quantities against a 0.10 bound. `MAX_ABS_SMD = 0.10` and `MIN_ASSIGNED_N = 200` were locked at the same moment and were mutually incompatible; setting the floor without a power analysis was the error.
  * **Why this is not a loosening:** the bound that *judges* the result is exactly what it was before any result existed. What moved is the precondition for evaluating the gate at all, in the **conservative** direction — more evidence required before balance may be certified, not less. It also makes the constant do the job its own comment claimed: at n=240 the gate said FAIL when the honest verdict was "cannot tell".
  * **Why 3500 and not 4000:** the criterion is the smallest n whose 95% Wilson *lower* bound clears a 95% pass rate (97.00% observed, 96.16% lower, 2000 trials). The lower bound rather than the point estimate, because a Monte Carlo pass rate is itself an estimate and choosing on the point estimate would clear the criterion by sampling luck about half the time. n=3000 does not clear it (93.75% / 92.60%).
  * **What breaks if reversed:** restoring 200 makes the gate a coin-flip that fails 99%+ of the time on a correct system, which is worse than no gate — it trains its reader to rationalise failures away, and it nearly triggered an unnecessary escalation to stratified assignment.

* **The balance power analysis had to be made reproducible before its result could justify a locked threshold**
  * **Why:** `_draw_rows()` minted ids with `uuid.uuid4()`, which reads `os.urandom` and ignores `random.seed`. Two runs at the same seed put n=3500 at 98.0% and 96.0% — straddling the criterion, so the chosen floor moved between runs. A locked threshold justified by a measurement nobody can replay is not justified, whichever number it lands on. Id generation is now seeded via `rng.getrandbits(48)` — the same 48 uniformly random bits `uuid4().hex[:12]` provides, so the assignment hash sees an input of identical shape and distribution — and verified stable across repeat runs before the floor was set.
  * **What breaks if reversed:** any future re-derivation of the floor gets a different answer and nobody can tell whether the system changed.

* **Two Phase 6 findings were WITHDRAWN, with their diagnoses kept rather than deleted**
  * **The "missing bank/psp columns" defect.** Filed during planning as live code breakage with a proposed `ADDITIVE_COLUMNS` patch. It was a stale database file — mtime ~30 hours *older* than the commit that added the columns — being read as evidence about the code. No patch was made. What survived is a different, real finding: the repository could not build its database from a clean checkout, because `a7cd6d2` added `bank`/`psp` to the payments INSERT without regenerating the tracked seed JSON. Fixed by regenerating; no code change needed.
  * **"The balance gate is nearly blind to small bias."** Filed at X5 from a detection curve parameterised by a probability-units bias knob rather than by the induced SMD the gate actually measures. A 0.05 bias induces ~0.042 SMD and a 0.10 bias ~0.086, both *below* the 0.10 the gate is told to enforce — not firing there is correct behaviour, and a gate that did would enforce a tighter threshold than the one locked. The tell was detection *falling* as n rose, which no real effect does.

# PHASE 6 EXIT GATE + PHASE 7 — LIVE INCREMENTAL ATTRIBUTION (2026-09-05)

* **Phase 6 was complete against EXECUTION_PLAN.md's DoD and NOT complete against `Phase_Acceptance_Test_Gates.md`**
  * **Why:** the acceptance-gate document sets a higher bar. Phase 6 had assignment and suppression evidence but **no observation evidence at all**, and three `[NEW]` gate rows — concurrent-assignment safety, duplicate-outcome safety, and the concurrency/duplicate-delivery fixture in the exit gate — had no test anywhere. Two documents, two different bars, and the narrower one had been treated as the finish line.
  * **What breaks if reversed:** a phase signed off against its own summary rather than against the document that defines its acceptance. The DoD audit at X6 was correct on its own terms and still insufficient.

* **Enabling the optimizer at `trigger_event` exposed three defects the ranked pathway had been hiding for the whole project**
  * **Why:** the optimizer was disabled at every entry point, so the ranked path had never executed against a live database. (1) `optimize._insert_row()` never reads `cursor.lastrowid`, so `recovery_decisions.candidate_id` and `recovery_candidates.selected` had **never been populated by anything** — which made Phase 6's counterfactual probe on `selected = 1` *vacuous*, reading 0 for control because nothing could set it rather than because suppression worked. (2) `trigger_event` hardcoded `method: None`, and with the opportunity's method unknown every method-bearing candidate reads as a payment-method *change* and is structurally non-executable, so the engine fell through to `escalate` in 400 of 400 cases — selecting an action scored at EIV −5088 while a retry scored +4048 sat unexecutable at rank 1. (3) The contact-hours rule is judged against `created_at`, so a run at 07:00 blocked every contact action and left `escalate` the only executable candidate.
  * **What breaks if reversed:** the incremental number would measure "escalate versus do-nothing", determined by a missing field and by what hour the operator happened to run the script, and would be reported as though it measured the optimizer's policy.
  * **Note (3) is not a defect** — the compliance rule working correctly. It is handled by pinning generation to midday, which suppresses no check and is disclosed in code, CLI output and evidence.

* **`candidate_id` recovery lives in `pipeline.py`, not in `optimize.py`**
  * **Why:** the three-line fix belongs in `_insert_row`, but `optimize.py` is frozen-adjacent and its one dated exception (2026-09-03, network health) is explicitly recorded as closed and as authorising no further change. The id is recovered in the caller instead, matched on `rank` — unique among one run's scored rows — rather than on the attribute tuple, which is unique only by convention. Same precedent as `derive_pruned_candidates()`.
  * **What breaks if reversed:** a frozen module's closed exception silently reopened for convenience.

* **`synthetic_potential_outcome` is its own outcome source, deliberately not folded into `payment_event`**
  * **Why:** every outcome this experiment has was drawn from the Data Factory's generator, not observed from a real payment system. The point of the column is that a reader can tell a generated outcome from a confirmed one *by query*. `incremental_attribution` refuses to report at all on a population mixing the two.
  * **What breaks if reversed:** "is this figure synthetic?" becomes unanswerable from the data, and presenting a synthetic result as production evidence is the single most damaging claim this project could make — named in the acceptance gates as a do-not-proceed condition.

* **The incremental figure is reported with a confidence interval that includes zero, and that is stated as the finding**
  * **The result:** incremental recovery rate **+0.0199, 95% CI [−0.0025, +0.0424]**; incremental ₹/opportunity +1,549.72, CI [−3,546.99, +6,646.43]; total +2,699,617 over 1742 resolved treatment opportunities. Recovery rates 0.8772 (1528/1742) treatment against 0.8572 (1507/1758) control.

Reporting the point estimate without its interval would be a claim this data does not support. Stated in PHASE7_NOTES.md rather than left for a reader to notice.
  * **Estimator:** difference in proportions (Wald) for the rate; difference in means (Welch, unpooled) for rupees — unpooled because an intervention that works shifts the treated arm's spread as well as its centre, and pooling would assume away the thing being measured.
